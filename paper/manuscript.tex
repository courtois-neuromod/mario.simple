\begin{abstract}
Video games are increasingly used as naturalistic stimuli in neuroscience and as benchmarks
in artificial intelligence, but their rich visuals confound the study of task-relevant
processing: a player's behaviour and a brain's response depend jointly on what the game
\emph{requires} and on how it \emph{looks}. We present a modified version of the NES game
\textit{Super Mario Bros.} in which the visual scene is reduced to its functional content while
the game itself is left untouched. Every decorative element (clouds, hills, bushes, trees,
fences, castle, water plants) is made transparent, and every object the player can interact
with (ground, bricks, question blocks, coins, pipes, platforms, enemies, items, the player, the
goal) is drawn as a flat square whose colour encodes its semantic category identically in every
level; moving objects are drawn as the exact rectangle of their collision box, and the few game
states that colour cannot carry (facing direction, dying, a kickable shell, an enemy that cannot
be stomped, a winged enemy) are encoded by simple shapes. The modification rewrites only the
graphics memory and the presentation tables of the game cartridge; program code, level data and
random-number generation are unchanged. We verify on
participant recordings from the Courtois NeuroMod \textit{mario} dataset that the simplified
game replays controller inputs frame-for-frame identically to the original, that savestates are
interchangeable between the two versions, and that all RAM-derived behavioural variables are
preserved. The simplified game therefore provides a within-subject visual-complexity control
for existing and future gameplay recordings, for fMRI, and for reinforcement-learning agents.

\section{Methods}
\label{sec:methods}

\subsection{Design goals}
\label{sec:goals}

The simplified game was designed under three constraints.
\begin{enumerate}
  \item \textbf{Functional transparency.} Any element with no effect on gameplay is removed from
  the image, i.e.\ rendered as the uniform backdrop. This includes clouds, hills, bushes,
  background trees, tree trunks and the stumps under tree-top ledges, mushroom stems, fences,
  chains, bridge guard-rails, the water surface line, sea plants, balance-lift ropes and pulleys,
  the end-of-level castle, fireworks and brick debris. The same rule is applied to the audio: all
  music is removed, and so are the decorative sound effects (fireworks, the end-of-level timer
  count, pipe entry).
  \item \textbf{Semantic colour coding.} Every element the player can interact with is drawn as
  a flat rectangle of a single colour, and the colour is a semantic category that is the same in
  every level regardless of the original day, night, underground or water palette
  (Table~\ref{tab:legend}). Moving objects are drawn as the exact rectangle of the collision box
  the game uses for them, so that what is seen is what the game reacts to
  (Section~\ref{sec:hitbox}); the game states that matter for play but that colour cannot carry
  are encoded by a few simple shapes (Table~\ref{tab:shapes}). Likewise every sound effect that
  carries game information becomes one constant tone per category, the tunes the game itself waits
  for become one to three plain tones of unchanged length, and star power is a continuous hum
  (Section~\ref{sec:sound}).
  \item \textbf{Logical identity.} Program code, physics, level layouts, enemy behaviour, RAM
  layout and random-number generation are untouched, so that controller recordings and savestates
  made on the original game remain valid on the simplified one, RAM-derived behavioural variables
  are identical, and humans and agents face exactly the same task.
\end{enumerate}

\subsection{The original stimulus}
\label{sec:original}

The reference game is the NTSC release of \textit{Super Mario Bros.} (Nintendo, 1985) as
distributed in the CNeuroMod \textit{mario} stimulus set\cite{paugam2025mario}, run under the
\texttt{fceumm} core\cite{fceumm} of \texttt{stable-retro}\cite{stableretro}, a maintained fork
of Gym Retro\cite{openai2018gymretro}. The stimulus set defines 22 playable levels (worlds 1--8,
stages 1--3; castle and water levels were excluded from the dataset) through emulator savestates,
a reward/termination scenario, and a map of RAM addresses to named variables (player position,
score, coins, lives, enemy states, power-up state, level and area identifiers). Participants'
gameplay is stored as \texttt{.bk2} files: the emulator's initial state plus the controller input
of every frame at 60~Hz, which the deterministic emulator turns back into the full audiovisual
stream and RAM trajectory. \TODO{cite the dataset numbers: 5 participants, 22 levels, N

\subsection{How the NES draws the game, and why it can be recoloured without changing it}
\label{sec:nes}

An NES cartridge holds two read-only memories\cite{nesdev}. \emph{PRG-ROM} (32~KB for this
title) contains the 6502 program, the level data and a number of small data tables.
\emph{CHR-ROM} (8~KB) contains the pixel shapes of 512 tiles of $8\times8$ pixels at 2~bits per
pixel: 256 tiles for sprites (moving objects) and 256 for the background. Colour is not stored in
the tiles: each pixel value 0--3 is an index into one of eight 4-colour palettes (four for the
background, four for sprites) held by the picture processing unit (PPU); index 0 is transparent
for sprites and the shared backdrop colour for the background.

The game never reads CHR-ROM: it only tells the PPU which tile to draw where. Collision,
movement, scoring and every other rule operate on \emph{metatile} identifiers (16$\times$16-pixel
block types) and object identifiers held in RAM, not on pixels. Palettes are only \emph{written}
by the game, at level load and for a few animations, from small tables in PRG-ROM, through a
write buffer in RAM (\hex{0300}--\hex{03FF}) that is flushed to the PPU during vertical blank.
Nothing in the game reads the palette back. Two consequences follow. Rewriting CHR-ROM changes
what is seen and nothing else. Rewriting the palette tables in PRG-ROM (and, as detailed below,
one table mapping metatiles to tiles and four constants selecting an object's sprite palette)
changes only the bytes that pass through the PPU write buffer and the sprite list, with no effect
on game state. Section~\ref{sec:verification} tests this claim empirically rather than relying on
it.

\subsection{Background tiles}
\label{sec:bg}

\textit{Super Mario Bros.} composes the background from metatiles, each defined by four tile
identifiers listed in four tables in PRG-ROM (one table per background palette, 101 metatiles in
total; CPU addresses \hex{8B10}--\hex{8CA3} in the annotated disassembly\cite{smbdis}). We dumped
these tables from the original ROM and used them to assign every background tile to the block
type(s) it belongs to (ground, brick, question block, pipe, cloud, bush, hill, \ldots), rather
than guessing from its picture. Each tile was then rewritten as either transparent (all pixels
index~0) for decoration, or a solid square of a chosen palette index (1, 2 or 3) for interactive
blocks; the index selects the semantic colour through the palettes of Section~\ref{sec:palettes}.
The flagpole shaft keeps its thin shape but is recoloured, and so is the coin icon of the status
bar, which takes the coin colour; text and the other HUD tiles are untouched. A Bullet Bill cannon
is made of three metatiles (the barrel, from which the bullets come out, a pedestal and a column)
that use the palette of the ground and the bricks, whose third colour is free: the barrel has a
colour of its own (launcher), the pedestal and the column are terrain.
Figure~\ref{fig:tilesheet} shows the complete tile sheet before and after.

Some tiles are shared between categories, so that no tile rewrite can serve both; for those we
edited the metatile-graphics table instead (42 bytes). Tile \hex{26} is both the fill of the
decorative hills and the inner column of every pipe shaft: the two pipe-shaft metatiles use the
pipe-edge tile instead (4 bytes). Tile \hex{47} is the breakable brick, the wall of the
end-of-level castle and the base of the springboard: the seven castle metatiles use the blank tile
(28 bytes), which makes the castle, a purely decorative object, disappear, and the two half-block
metatiles under a springboard, which are solid and cannot be broken, use a terrain tile (4 bytes).
Tiles \hex{A2}/\hex{A3} are the flagpole shaft and the vertical rope of the balance lifts, which is
decoration: the rope and pulley metatiles use the blank tile (6 bytes). This table is read only
when the game writes a new screen column into the PPU write buffer. The rope is the one piece of
background that the game also draws without a metatile: while a balance lift moves down, a routine
queues the two rope tiles above it directly; its four immediate operands now name the blank tile.

\subsection{Sprite tiles}
\label{sec:sprites}

Every sprite tile below \hex{F6} becomes a flat rectangle (the floating score digits
\hex{F6}--\hex{FF} keep their glyphs). The colour index a tile receives depends on which object
draws it, and this was \emph{measured} rather than assumed. The game builds its sprite list in RAM
(\hex{0200}--\hex{02FF}) and keeps, for the player, each of six enemy slots (one of which hosts
the power-up object), bumped blocks, bubbles, fireballs and miscellaneous objects, the offset of
their entries (\hex{06E4}--\hex{06FB}); enemy identifiers and active flags are at
\hex{0016}--\hex{001B} and \hex{000F}--\hex{0014}. Replaying 66 participant recordings (three
per level, all 22 levels) on the original ROM and reading these locations every third frame gave,
for each of the 512 sprite tiles, the object that drew it and the sprite palette it was drawn
with. The resulting map covers the player (86 tiles), 14 enemy types, the four power-ups,
fireballs, coins, hammers, the flag, vines, moving platforms, springboards, fireworks and the
castle flag; tiles never observed default to the enemy category.

Because a sprite's palette is chosen by the game per object, tiles of different categories can
share a palette (the mushroom and the Spiny both use sprite palette~2, for instance). Categories
are therefore separated by \emph{index} within a palette (enemies index~2, items index~1,
platforms index~3), and the palettes of Section~\ref{sec:palettes} give each index its colour.
The player's tiles use index~1 because the star-power effect rotates the player's palette
\emph{attribute} through the four sprite palettes: with index~1 he flashes light blue, dark
green, green and grey rather than enemy red.

Four palettes with three indices each give twelve sprite colours, but the game's own palette
assignments crowd some categories into the same palette (coins popping out of blocks, fireballs,
the mushroom and the Spiny all use sprite palette~2). Where that prevented a category from having
its own colour, we changed the palette the game assigns to the object (Table~\ref{tab:changes}).
The game chooses a sprite's palette in three ways, all of them presentation data that reaches
nothing but the sprite list. (i)~An immediate operand of the object's drawing routine: the
fireball now uses the player's palette (index~3); the coin popping out of a block (two sprites)
and the ``200'' that follows it use palette~3 (index~3), as do the floating score numbers (coin
colour); the vine uses palette~3 (index~2, interactive); the fire flower and the star use the
player's palette (index~3, the fire-player deep blue, and index~2, pale pink), and the routine that
cycles their top row through the four palettes every two frames now always selects palette~0.
(ii)~The enemy attribute table, one byte per enemy graphic, which the enemy drawing routine ORs
into the sprite attribute: Buzzy Beetle, Goomba, Bloober and Bullet Bill leave palette~3 for
palette~2 (both hold the enemy colour at index~2), which frees index~2 of palette~3 for the
interactive colour, and the three springboard frames enter palette~3. Two special cases of that
routine bypass the table and needed their own operand changed: the cannon-fired Bullet Bill and the
two lower rows of the springboard. (iii)~Small per-object tables: the power-up attribute table
(the 1-up and the super mushroom share their tiles and are told apart by the game with the palette
alone, 1 versus 2, so index~1 of palette~1 is a dedicated 1-up colour) and the hammer attribute
table.

A block that is hit from below is drawn as a sprite while it bounces, by one routine: it draws the
brick tiles and, if the block is turning into a used block (a question block, a brick that held an
item, a hidden block), redraws it with the used-block tile. The bouncing block is thus already
what it becomes, and is coloured accordingly: the used block uses palette~2 (index~3, terrain),
the brick keeps the game's own palette~3, whose index~1 is the brick colour. Brick debris,
fireworks, the castle flag and the air bubbles of the underwater areas are transparent. Sprite~0,
two rows of pixels that complete the coin icon of the status bar and that the game uses to time the
screen split below the status bar, keeps its shape and takes the coin colour.

\subsection{Sprite rectangles fit the collision box}
\label{sec:hitbox}

\textit{Super Mario Bros.} does not derive collisions from the art. For every sprite object the
game computes a collision box as the object's relative screen position plus one of 12 four-byte
entries (left, top, right and bottom offsets) of a table in PRG-ROM, selected by a per-object
control byte set at initialisation (small, big and crouching player; ``tall'' and ``small''
enemies; fireball; hammer; Bowser's flame; Bowser; three sizes of lift). The boxes live in RAM
(\hex{04AC}--\hex{04DB}), and the sprite--sprite collision routine compares them with inclusive
edges. The tiles of the same object are drawn at fixed offsets from the same position, in one to
three rows of two $8\times8$ tiles. For each tile there is therefore a fixed set of pixels that
lie inside the box, and the tile can be \emph{carved} to those pixels: opaque inside the box,
transparent outside.

The geometry was measured rather than transcribed from the disassembly. The same 66 recordings
were replayed on the original ROM while reading, every second frame, the sprite list, the
object-to-sprite offset tables and the live boxes, recording for each drawn tile the owner object
and state, the tile's offset from the top-left corner of the owner's box, and the box size, with
the sprite's horizontal and vertical flip bits folded back into tile space (the game mirrors the
right-hand copy of symmetric tiles with the flip bit, so a tile used on both sides of an object is
consistent once flips are folded). Objects whose state disables collisions (defeated enemies
falling off screen, squished Goombas) and the frames of the grow and shrink animations were
excluded. The dominant geometry per tile is a 187-entry table in the generator; the tiles of the
big swimming player, who never occurs in the dataset, were placed from the graphics tables, and
castle objects (Bowser, Podoboo, flames, fire bars) were left as full squares. Every drawn
rectangle was then compared with its box on the simplified ROM (Section~\ref{sec:verification}),
which corrected the entries of the Bloober, the hammer and the Bullet Bill. Table~\ref{tab:boxes}
gives the resulting box sizes next to the size of the drawn sprite. For every object of its first
four rows the box lies inside the drawn sprite, so the carve is exact; the exceptions are listed
in Section~\ref{sec:verification}. One object needed more than a tile rewrite to be drawn on its
box. The hammer is a pair of sprites that spins around an $8\times8$ box located at the object's
position: in every frame half of one sprite lies in the box and the other sprite lies outside it,
and each tile takes both roles in turn, so no carving fits; the seven 4-byte tables that give, per
animation frame, the offsets, tiles and attributes of the two sprites now put one full tile on the
box and make the other sprite blank. We used the exclusive convention (a box of width
$\mathit{right}-\mathit{left}$), which yields the familiar sizes; because the game compares edges
inclusively, two boxes also register a collision when they merely touch, i.e.\ the effective box
is one pixel larger on each side than drawn. The player's collisions with the \emph{terrain} are
not box-based at all: the game probes points at $x+2$ and $x+13$ and, vertically, at $y+4$ (big)
or $y+18$ (small) for the head and $y+32$ for the feet, so the terrain-relevant region is a few
pixels larger than the enemy box.

The visual consequence is that objects become noticeably smaller than their sprites: a Goomba is
a $10\times6$ sliver at the bottom of its former $16\times16$ body, and small Mario a
$10\times12$ block whose top is 4~px below the top of his head (Figure~\ref{fig:hitbox}). This is
faithful to what the game reacts to and is the purpose of the change; the generator can also
produce full-size squares.

\subsection{Shape cues for game state}
\label{sec:shapes}

Colour identifies the category of an object; a few states that matter for play are conveyed in
the original only by drawings. We surveyed every such distinction (Table~\ref{tab:semantics}) and,
where colour slots were exhausted, encoded it with a simple shape drawn within the same rectangle
(Table~\ref{tab:shapes}, Figure~\ref{fig:cues}). The player's facing direction is a $2\times2$
transparent hole 2~px in from the front edge and 2~px below the top of the box: the tiles are drawn
facing right and the game sets the horizontal-flip bit when he faces left, so the hole moves with
him. Koopa and Buzzy shells and the player's death pose are hollow (a 2-px ring), i.e.\ ``an empty
or inert body''. The Spiny, its egg and the Piranha Plant, the enemies that hurt when stomped, have
a toothed top edge. The two Paratroopa wing tiles, which sit in the row above the box, carry an
$8\times2$ bar 1~px above the box; it is the only opaque pixel drawn outside a collision box, and
it is on one side of the enemy only because the other tile of that row is the Koopa head shared
with the walking Koopa. The squished Goomba, which has no collision, is a $16\times4$ bar on the
ground, and the springboard, which the game handles by position rather than by a sprite box, is
striped, in the interactive colour.

\subsection{Palettes}
\label{sec:palettes}

The game keeps four 32-byte palette sets (water, ground, underground, castle), three 4-byte
variants for snow and mushroom areas, a 12-byte player palette table (Mario, Luigi, fire Mario),
an 8-byte backdrop-colour table, and two small tables used to animate question blocks and coins by
rewriting background palette~3 every 8 frames. All of these were overwritten so that every
palette index means the same category everywhere (Table~\ref{tab:palettes}). The backdrop is
black in every area, including the ``WORLD x-y'' screens. Terrain is white rather than the
natural brown so that it sits far from enemy red, two adjacent NES hues of similar brightness,
and the player is blue. The fire-player colour (\hex{12}, a deep blue) was chosen next to the
player's light blue so that the change of state is visible while keeping the object in the
``player'' family; fireballs and the fire flower share it. HUD text shares the terrain white.
Two choices are a compromise. The interactive dark orange (\hex{17}) is the NES hue next to the
enemy red, at the same brightness; the two never share a shape (question blocks are static
$16\times16$ squares, enemies smaller moving rectangles), and an earlier version that used the
lighter orange \hex{27} next to a coin yellow \hex{28} made question blocks read as coins. The
launcher dark red (\hex{06}) is in the enemy family on purpose: a barrel is where enemies come
from. Question blocks and coins do not pulse as in the original: the tables that the game rotates
into background palette~3 hold a single colour.

\subsection{Sound}
\label{sec:sound}

The sound engine occupies the end of PRG-ROM and runs inside the NMI handler after the game logic
of the frame. Game logic drives it through six queue bytes (which effect or tune to start) and reads
back a single byte of its state, \texttt{EventMusicBuffer}, which it polls for zero in two places:
while Mario falls off the screen after dying (the death tune must end before the lose-life routine
runs) and in the end-of-level sequence (the level-clear tune must end before the next area loads).
Everything else the engine touches is its own state and the APU registers, which the CPU cannot
read. The audio was therefore simplified under the same three constraints as the image. The six
area tunes are replaced by silence through the table from which the game selects them; the
star-power tune becomes a low continuous hum; the tunes the game waits for (death, level clear,
castle clear, victory, game over, time warning) are rewritten as data for the unchanged music
handler, as one to three plain tones followed by rests with exactly the frame count of the original
tune, parsed from the original data and asserted at build time. The three per-channel sound-effect
handlers of the original (about 730 bytes, one hand-written envelope or sweep per effect) are
replaced by one table-driven routine of 267 bytes, assembled at build time by a minimal assembler
included in the generator, which plays one constant tone (pitch, length, square duty or noise
period) per queue bit. Cues are assigned per visual category: jump (also the swim stroke), block
hit, enemy defeated, player shrinks, fireball, flagpole slide, coin, item emerging (also the vine),
power-up collected, extra life, Bullet Bill fired, brick shattered and Bowser's flame (both noise).
Three effects share a queue bit with an unrelated event in the original (pipe entry with injury,
fireworks with the Bullet Bill blast, the swim stroke with the stomp); at the four gameplay sites
concerned the operand naming the bit is changed so that the decorative events land on unused bits
mapped to silence, and each site overwrites the register right after the store. The sound engine's
RAM thus differs from the original ROM during play and is masked by the verification of
Section~\ref{sec:verification}; every other byte, i.e.\ everything game logic computes, must still
match. Savestates captured mid-level carry the tune that was playing; the companion tool that
rewrites their palette also sets the engine idle.

\subsection{Reproducibility}
\label{sec:repro}

The simplified cartridge is generated deterministically from the original by a single script
(\texttt{code/simplify\_rom.py}) that contains the tile classification, the colour table and the
list of PRG patches; every PRG patch asserts the original bytes before writing. The input is the
original ROM of the \textit{mario} stimulus set (MD5 \texttt{811b027e\ldots}); the output has MD5
\texttt{a408d0f1\ldots} (\texttt{f08e5c0b\ldots} with the original sound). Companion tools reproduce the sprite survey
(\texttt{survey\_sprite\_tiles.py}), the collision-box survey (\texttt{hitbox\_survey.py}), the
three checks of Section~\ref{sec:verification} (\texttt{verify\_replays.py},
\texttt{audit\_colours.py}, \texttt{audit\_sound.py}), the rewrite of the palette, sound state and
drawn screen of savestates (\texttt{fix\_state.py}) and the figures (\texttt{make\_figures.py}). The stimulus is distributed as a drop-in replacement of the
\textit{mario} stimulus set: same savestates, scenario and RAM-variable map, different
\texttt{rom.nes}.

\subsection{Verification}
\label{sec:verification}

Three tools replay recordings with the same emulator and check, respectively, that the game logic
is untouched, that the picture is what the legend says, and that the sound is.

\paragraph{Game logic.} We tested the claim of Section~\ref{sec:nes} directly. A participant
recording is replayed on the original and on the simplified ROM, starting from the recording's own
initial savestate, and the 2~KB of console RAM are compared after every frame. The comparison is
made on the frames where the CPU is parked in the game's idle loop, i.e.\ where all the logic of
the frame has run; on the few frames where it has not (the game takes more than one frame to wipe
its memory when an area loads), the two ROMs can be a few CPU cycles apart because their sound
code differs, and those frames are skipped and counted. Differences are tolerated only in the
bytes that describe what is drawn or played: the sprite list (\hex{0200}--\hex{02FF}); the two PPU
write buffers (\hex{0301}--\hex{033F}, \hex{0341}--\hex{0362}), whose length bytes must be equal;
the addresses above the second buffer (\hex{0363}--\hex{03FF}) only where it reaches while an area
loads, since during play they hold game variables; one zero-page scratch byte (\hex{0004}) through
which the drawing routines pass a sprite's palette; the sound engine's own state
(\hex{00F0}--\hex{00FF}, \hex{07B0}--\hex{07CA}), of which game logic reads back only
\texttt{EventMusicBuffer} to wait for tunes whose length is preserved; and the CPU stack
(\hex{0160}--\hex{01FF}), which is empty in the idle loop. A savestate is also taken halfway
through the run on the original ROM, loaded into the simplified ROM, and the remaining input is
replayed to check that the run continues identically. The same procedure applied to a build with
the original sound must yield identical sound state and stack as well, and to a graphics-only
build (tile changes without any PRG patch) byte-identical RAM on every frame, which tests the
emulator side of the argument.

\paragraph{Picture.} RAM identity says nothing about the picture. A second tool replays recordings
on the simplified ROM and checks the picture object by object, using the game's own memory to know
what each thing on screen is: every sprite of the sprite list is attributed to the object that
drew it through the game's sprite-offset tables, and the colours of its opaque pixels must be those
of that object's category; every visible $16\times16$ cell of the name table must be drawn in the
category colour of the block that the game holds at that place in its block buffer, and be empty
where it holds none; the rectangle drawn for each object that has a live collision box is compared
with that box, edge by edge; and every pixel of the rendered frame must have a legend colour. Its
expectations are written from the game's logic, independently of the tile tables of the generator.

\paragraph{Sound.} The emulator's savestate holds the registers of the sound chip, so what each
channel does on a frame can be read exactly. A third tool checks that every sound effect sets its
channel to the pitch, duty and volume of its cue, keeps sounding with those values on every frame
and lasts its number of frames, that a channel is audible only while an effect or a tune plays on
it, and that each tune sounds only its notes.

\paragraph{Savestates.} Three properties of the recordings matter for rendering them on the
simplified ROM: a recording's initial savestate carries the PPU palette, the state of the sound
engine and the name tables (the tiles of the screen already drawn) of the moment it was captured,
i.e.\ what the original ROM had produced. 3{,}231 of the 3{,}374 recordings start on the
``WORLD x-y'' screen, so the level is drawn and its palette written about 120 frames later by
the simplified ROM, but that first screen is drawn with the stored palette (original player
colours). The other 143, all of level 4-1, whose level state was saved in gameplay, would keep the
original colours until the next area change, go on playing the original tune until the end of its
section, and show the castle next to which that level starts, drawn by the original ROM, as a wall
in the brick colour. A companion tool rewrites the 32 palette bytes, sets the sound engine idle
and redraws the cells of the name tables that the simplified ROM draws differently (it reads what
each cell is from the game's block buffer in the same state); the run is RAM-identical afterwards,
and the level savestates of the stimulus set are distributed rewritten.

\paragraph{Residual differences between rectangle and box.} Where a collision box sticks out of
the drawn sprite, the missing pixels are not drawn, because that would require additional sprite
entries: Hammer Bro's box extends 4~px below his feet, lifts have a 5-px landing-tolerance zone
under the bar, a resting shell has a 1-px strip of box above it, and Bowser has a box on his front
half only. Smaller residuals: the Spiny egg is drawn $10\times8$ for a $10\times6$ box, because
its four quadrants are two tiles, each used once as is and once mirrored at another height; the
Bullet Bill of the ``frenzy'' levels (5-3 and 6-3) is drawn 1~px below its box, because it shares its tiles with
the cannon-fired one, which the game draws 1~px higher; a Lakitu that the game re-creates after
one was defeated has the $4\times4$ box of Bowser's flame, whose set-up routine it shares, and
is still drawn $12\times12$; and the box can lag the rectangle by 1 to 3~px because the game
computes it before the final position update of the frame.
